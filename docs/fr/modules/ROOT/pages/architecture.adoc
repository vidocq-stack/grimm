= Architecture
:description: Structure interne de Grimm — découpage des modules, JPMS et flux d'exécution.

== Séparation des responsabilités

Grimm suit une séparation stricte inspirée des autres composants Vidocq :

- `grimm-core` : logique pure Java (scan, génération de schémas, merge, sérialisation)
- `grimm-cdi-vauban` : intégration CDI, orchestration au démarrage et endpoint HTTP

Cette séparation permet de tester `grimm-core` sans conteneur CDI.

== Modules JPMS

- module `io.vidocq.grimm.core`
- module `io.vidocq.grimm.cdi.vauban`

`grimm-core` expose ses classes internes de manière qualifiée vers `grimm-cdi-vauban`.

== Flux d'exécution

1. `StaticFileReader`
2. `ModelReaderInvoker`
3. `AnnotationScanner`
4. `ModelMerger`
5. `FilterInvoker`
6. `GrimmModelCache`

Le modèle final est calculé une fois puis réutilisé pour toutes les requêtes `/openapi`.

== Contrainte dépendances

En production, Grimm n'embarque pas de bibliothèques d'implémentation OpenAPI tierces
(SmallRye, Swagger Core, Jackson, Snakeyaml).

== Concurrence

Le projet impose un style compatible virtual threads :

- pas de `synchronized`
- pas de `ThreadLocal`
- usage ciblé de primitives non bloquantes / locks explicites
